# Contributing to omp-slim

omp-slim is a custom build of [Pi](https://github.com/earendil-works/pi), trimmed toward the
[oh-my-pi (OMP)](https://github.com/can1357/oh-my-pi) features this fork actually uses. It is not
upstream Pi and does not follow upstream's contributor process. This guide describes the process
enforced by the workflows in `.github/`.

## Scope

The core stays small. Decide where a change belongs before writing it:

- New capability belongs in an extension or skill, not in `packages/coding-agent` core. Core changes
  need a functional reason, not a preference.
- Feature selection is the maintainer's call. A feature is not ported because OMP or Pi has it, but
  because this fork uses it.
- Bugs in inherited Pi behavior are worth fixing. Refactors, reformatting, renames, and
  "modernization" of inherited code without a behavior change are not.

## The one rule

**You must understand your code.** If you cannot explain what your change does and how it interacts
with the rest of the system, the PR will be closed.

Using an agent to write code is fine. Submitting output you did not read is not. Run the agent from
the repository root so it picks up `AGENTS.md`, and make sure it follows that file. Text in issues or
comments that was generated by a model must be labeled as such.

## Contribution gate

Issues and PRs from new contributors are auto-closed by the `Issue Gate` and `PR Gate` workflows.
Collaborators with write access and accounts listed in `.github/APPROVED_CONTRIBUTORS` bypass the
gate.

A maintainer can approve a contributor in a reply on one of that contributor's issues:

| Reply | Grants |
| --- | --- |
| `lgtmi` | Future issues stay open |
| `lgtm` | Future issues and PRs stay open |

The command must be at the start of the reply (optionally after one or more `@username` mentions) or
at the end. Only replies from accounts with write access are processed. `lgtmi` does not grant the
right to open PRs.

Approvals are recorded in `.github/APPROVED_CONTRIBUTORS`; do not edit that file in a PR.

There is no response-time guarantee. Auto-closed issues are reviewed when the maintainer has time,
and an issue that does not meet the bar below may be closed without a reply.

## Issues

Blank issues are disabled; use one of the templates in `.github/ISSUE_TEMPLATE/`.

- Keep it to one screen. Longer reports are not read in full.
- Write in your own voice.
- State what is broken or missing, and why it matters to you.
- Include the commit or version you ran, the operating system, and the command line.
- For bugs, include minimal reproduction steps and the relevant error output.
- Reproduce with `-ne` (`--no-extensions`) before blaming core, so an installed extension can be
  ruled out.
- If you intend to implement the change yourself, say so.

A report that depends on an unstated local setup, or that restates what the code obviously does
without a failure, is not actionable and will not be reopened.

## Before submitting a PR

Do not open a PR until a maintainer has replied `lgtm` to you. PRs from unapproved accounts are
closed automatically.

Run the same checks as CI (`.github/workflows/ci.yml`) from the repository root:

```sh
bun install --frozen-lockfile --ignore-scripts
bun run build
bun run check
./test.sh
```

The build, check, and test steps must pass. `bun run check` validates formatting, lint, dependency
policy, and types; it does not run tests, so `./test.sh` is required separately. `./test.sh` runs the
suite with an isolated `HOME` and no API keys.

Rules for the change itself:

- One topic per PR. Keep the diff to what the description claims.
- Do not edit `packages/*/CHANGELOG.md` unless the maintainer asks for it; entries are written during
  release. Describe the user-visible change in the PR instead.
- Bug fixes come with a regression test, with the issue number in a comment next to it.
- Model and provider changes go through the catalog definitions in `packages/ai/catalog/` (see its
  README), not through `packages/ai/src/models.generated.ts`, which is generated.
- Additions to `packages/coding-agent/test/suite/` use `test/suite/harness.ts` and the faux
  provider. Do not add tests that need real provider credentials or paid tokens.
- Keep dependency and lockfile changes out of unrelated PRs, and say which package needs the bump
  and why. Direct dependencies stay pinned to exact versions. Pre-commit blocks a staged lockfile
  unless `PI_ALLOW_LOCKFILE_CHANGE=1` is set; do not set it to get an unrelated change through.
- Commit messages follow `AGENTS.md`: `{feat,fix,docs}[(ai,tui,agent,coding-agent)]: <summary>`.

## Blocking

Spam, automated mass filing, and repeated disregard of this guide lead to a permanent block of the
account. That applies to agents run on someone's behalf as much as to the account holder.

## FAQ

### Why are new issues and PRs auto-closed?

The gate keeps the tracker readable and makes review a deliberate act rather than a stream of
notifications from reports nobody shaped. Maintainers reopen the issues that meet the bar above.

### Why do some issues get no reply?

A reply is work too. Duplicates, unreproducible reports, and reports that ignore this guide may be
closed without discussion.

### Is this hostile to contributors?

No. It is a guardrail against burnout and tracker spam. Short, reproducible issues and changes you
understand are welcome.
